#### Wall system rework: pentominoes, dynamic ramping, and shrinking -- v4.4.0
- Obstacle walls spawn as pentomino-shaped 5-cell clusters instead of single cells, choosing randomly from the 12 free pentominoes (I, L, F, N, P, T, U, V, W, X, Y, Z) and applying one of 8 orientations (4 rotations plus mirror-image variants) for visual and tactical variety. The placement logic mirrors the old single-cell cell picker (200 random tries, rejection-sampled to avoid overlaps and sealing) but validates all 5 cells at once: bounds, occupancy, anti-sealing guard (see below), and minimum head distance. All 5 cells share a single `Wall.id` so they pulse/throb in visual sync during the telegraph and despawn phases.
- Wall piece count now ramps dynamically with snake length to keep the board challenging as snakes grow: every living snake adds +1 piece to `walls.maxConcurrent`'s base count for each 20 units of body length past 40 (a 60-long snake adds 1, an 80-long adds 2, a 100-long adds 3, etc.), summed across all players. The total wall cells are also capped so they never exceed the combined body length of all living snakes -- a lobby of short/few snakes can't get buried in obstacles. Pieces are atomic (5 cells, never split), so the cap checks headroom for a whole piece rather than just whether already over, preventing overshoot on the very first spawn in a short-snake game.
- The anti-touching guard between separate wall pieces was widened from "not orthogonally adjacent" (Manhattan distance <= 1) to "at least a 2-cell gap" (distance <= 2 rejected), giving snakes more room to navigate between obstacles.
- Wall count actively shrinks when the budget drops -- e.g. as players die or snakes shrink back down -- rather than passively waiting out each piece's full lifetime. A `wall_cell_budget` function is recomputed every sim tick by `shrink_walls_to_budget` alongside the spawner, and any pieces exceeding the new budget are retired oldest-first (by spawn order): pieces still in their telegraph ("warn") window are dropped outright (never a real hazard yet); solid pieces are expedited into their normal despawn-telegraph fade so the disappearance still reads on screen instead of snapping out instantly.
- The wall warning telegraph ("warn" state) visual was changed from a pulsing flat hazard-orange full-tile fill to a small pixel-art red "!" (5x5 sub-grid, only the glyph pixels flash). The old flat orange read too close to the speedBoost powerup tint (#f50) at a glance (maintainer feedback), and the new glyph is more visually distinct. The throb period was also slowed (~1.3s vs the old ~0.5s) with a bounded alpha floor (0.55-1.0 instead of 0.35-0.7) to avoid any hard strobing that could trigger photosensitive reactions. The solid and fading spike-trap states are unchanged. Implemented identically across both renderers (`public/js/render2d.js` and `wasm/renderer.ts`) for pixel parity; the parity bench holds at <0.1% differing pixels across all scenarios.
- Entirely server-side rework of `server-rust/src/sim.rs`: new `PENTOMINOES` constant, `transform_pentomino` orientation handler, `wall_cell_budget` budgeting function, `shrink_walls_to_budget` retirement logic, and a complete rewrite of `maybe_spawn_wall` to place pentomino clusters instead of single cells. Wall and snap protocol unchanged; tests pass: all 19 `tests/pw_*.js` suite runs clean, including `tests/pw_walls.js` (which drives walls via the deterministic test hook, unaffected by the spawner logic), and live browser smoke on both renderers.

#### Legacy JS server tree removed; installer cleans up its own swap file -- v4.3.0
- The old JavaScript server (`server.js`, `server/*.js`, `powerups/*.js`) was deleted from the tree. It had been kept around as reference since the v4.0.0 Rust rewrite, but every code path that could still reach it was gone -- `tests/helpers.js` `startServer` now throws a clear "build the binary first" error instead of silently falling back to `deno ... server.js` when `server-rust/target/release/multisnake-server` is missing, so a test run can no longer accidentally exercise the retired implementation. `package.json` was trimmed down to version data only (dropped `main`/`scripts`/`dependencies`, which described the deleted Node entry point and its one dependency), and every remaining source comment that pointed at a `server.js`/`server/*.js` file or function (in `public/js/main.js`, `predict.js`, `render2d.js`, `ui.js`, plus `.gitattributes` and `build-info.json`) was updated to point at its `server-rust/src/*.rs` equivalent instead.
- `install.sh`'s low-resource swap file (added in v4.2.0 to get the Rust compiler through a build on a sub-2GiB box without being OOM-killed) is now torn back down once the build finishes: `swapoff`, the file deleted, and its exact `/etc/fstab` line removed, so a low-RAM install no longer leaves 2GB of disk permanently committed to an active swap device it only needed for a few minutes. This only ever touches swap the installer itself activated during the run (`install-lib/resources.sh` `maybe_add_swap` now tracks that in `SWAP_MANAGED_BY_US`) -- swap that already existed on the host, or that the operator declined to let the installer manage, is never removed. Set `KEEP_SWAP=yes` to keep it around for a future run instead of tearing it down. New `maybe_remove_swap` function in `install-lib/resources.sh`, called from `install.sh` right after the build step succeeds; left in place on a build failure in case a retry wants it.

#### Installer: low-RAM support, prebuilt-binary fallback, install-lib split -- v4.2.0
- A maintainer running the installer on a ~969MiB-RAM box hit a second, deeper variant of the v4.1.1 toolchain bug: `rustup default stable` would report success ("using existing install", "default toolchain set to...") while the toolchain directory itself was left corrupt (a partial download with no manifest file), so `rustc --version` kept failing afterward with `Missing manifest in toolchain 'stable-...'`. The repair branch now verifies through the proxy a second time after `rustup default stable`, and if it is still broken, force-reinstalls the toolchain from scratch (`rustup toolchain uninstall stable` + `rustup toolchain install stable --profile minimal` + `rustup default stable`) rather than trusting rustup's own "success" report. This toolchain repair logic stays inline in `install.sh`'s step 2 rather than moving to `install-lib/` (see below), since it is core to the numbered install flow, not optional or reused elsewhere.
- The same low-memory box also risked the Rust compiler getting OOM-killed outright during `cargo build --release`, since parallel codegen threads plus cross-crate thin LTO can peak well past 1GB of RSS on a single vCPU. Below 2GiB of detected RAM (`/proc/meminfo`, override `LOW_RESOURCE=yes/no`), the installer now offers to create a 2GB swap file (`CREATE_SWAP=no` to decline) before any build work starts, and forces the release build to a single cargo job with LTO disabled (`CARGO_BUILD_JOBS=1`, `CARGO_PROFILE_RELEASE_LTO=off`, `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16`, niced/ioniced so a concurrent SSH session stays responsive) -- that combination caps peak memory, not just wall-clock time. If the source build still fails (or `USE_PREBUILT=yes` skips it outright), the installer now falls back to downloading a prebuilt `multisnake-server-linux-x86_64` binary from the latest GitHub Release instead of leaving the host with no server at all.
- To make that fallback possible, `.github/workflows/release.yml` now builds a standalone Linux x86_64 server binary on every tagged release (via the same self-contained `rustup.rs` install `install.sh` itself uses, so no third-party Rust-setup Action is needed) and attaches it alongside the existing source archives. The installer also now writes a completion flag (`install-ok`, a timestamp, under `STATE_DIR`) only as the very last line of the script, cleared at the start of every run -- a re-run that finds the previous attempt's flag missing prints a notice pointing at `USE_PREBUILT=yes` rather than leaving the operator to guess why the build keeps failing.
- `install.sh` itself was getting long and expensive to read/edit as a single file (1142 lines), so the hostname/simHz/maxPlayers/debug prompts, port selection and stale-vhost/crash-loop detection, all of the low-resource handling above, and the TLS/certbot setup were split out into `install-lib/{prompts,network,resources,tls}.sh` plus a small `common.sh` for helpers used more than once (a `truthy`/`falsy` yes-no normalizer, `port_is_free`). `install.sh` is now ~600 lines and just orchestrates: it sources these from a local checkout directly, or -- since the `curl | bash` one-liner has no checkout yet -- curl-fetches each file individually from the same branch first. See `install-lib/README.md` for what lives where.

#### Installer: repair a half-installed Rust toolchain instead of dying -- v4.1.1
- A maintainer hit a half-deployed box: re-running `install.sh` printed `rustup could not choose a version of rustc to run, because one wasn't specified explicitly` and aborted with nothing upgraded. Root cause was an interrupted first install -- rustup writes its `cargo`/`rustc` proxy shims into `${CARGO_HOME}/bin` before it finishes downloading the actual stable toolchain, so a network drop, a ctrl-C, or an OOM kill between those two steps leaves the proxies on PATH with no default toolchain configured. The installer's toolchain step only checked `command -v cargo` to decide whether Rust was "already present," which is true for the proxies alone; it then ran the update branch (`rustup update stable`, which does not set a default) and the very next line, a bare `rustc --version`, failed and took down the whole script under `set -euo pipefail` -- and every subsequent re-run hit the identical dead end, since nothing about that state changes on its own.
- The check now probes THROUGH the proxy (`rustc --version`, not just `command -v cargo`) to tell a working toolchain apart from bare shims, and repairs the half-installed case with `rustup default stable` -- which both downloads the stable toolchain if it is still missing and sets it as the default, exactly the state a clean `rustup-init` run would have produced. A healthy existing install still takes the untouched update path. `install.sh` (~line 550).
- Also adds `tests/pw_solospawn.js`, a regression guard for the powerup pickup spawner clarifying a related report that turned out not to be a bug: solo play (one player seated) keeps spawning every non-blueShell pickup type; with only blueShell enabled, a lone player correctly gets nothing (the `>= 2 seats` presence gate holds even when blueShell is the sole candidate); and blueShell spawning resumes the moment a second player joins. No server code changed for this part -- it was a perception issue (solo pickup cap is 1, so one uncollected pickup blocks the next spawn; the stock spawn interval is 8s), and the test locks the intended behavior in against a future regression.

#### Wormhole rework: directional phasing + portal FX -- v4.1.0
- The Wormhole powerup's rescue logic was replaced end to end, following a diagram the maintainer supplied specifying the exact geometry for each collision shape. The old behavior teleported the snake to whichever safe spot scored best across every cardinal direction plus the board's mirror point -- a "best available exit," not tied to how the snake got into trouble. The new behavior is directional phasing: on a fatal collision the snake keeps its exact movement vector and phases straight through whatever it hit, coming out the far side still moving the same way. A board edge wraps to the opposite edge on the same row or column (torus-style); a dynamic grid-decay wall, a run of the snake's own body, or a stretch of another player's snake are all phased through by the identical spatial walk, including several consecutive segments and obstacles stacked one behind another (a wall immediately past a board edge, or a second snake's body right behind the first) -- no special-casing needed, since the walk simply keeps stepping until it clears every occupied cell in its path.
- A cell only counts as a valid landing if it is "realistically escapable": at least `wormhole.lookaheadDepth` (3) consecutive free, in-bounds cells open up along the travel direction or one of the two perpendiculars (deliberately never the reverse, since the tail is still threading in behind the head through the entry). This stops the rescue from dropping a player into a one-cell pocket wedged between two obstacle runs -- those gaps are passed over in favor of the next real opening. If nothing on the whole wrapped line clears that bar, the roomiest cramped gap seen is used as a fallback; if the line is entirely blocked, a whole-board search finds the nearest cell that does pass, so the player always comes out somewhere survivable rather than the wormhole simply fizzling.
- A purple portal marker now appears at both the entry point (the cell that was hit, or the board-edge cell the head was sitting against for a wrap) and the exit point (the landing), matching the effect from the reference diagram. The pair is tracked server-side (`S.portalFx`, broadcast as `portalFx: [{id, x, y, ownerSlot}]`) and stays visible for as long as the snake's tail is still threading through the entry, with a short 600ms linger after the drain finishes so the closing reads clearly on screen instead of popping out instantly. Both renderers draw a pulsing ring with a soft core in the wormhole's existing purple, layered on top of snake bodies (the entry portal should read as visibly "swallowing" the snake, not sit hidden underneath it); the wasm core and the 2D fallback share the exact same pulse and geometry formulas for pixel parity.
- Server: `server-rust/src/powerups.rs` (`attempt_wormhole` rewritten around the unified spatial walk; new `PortalFx`-producing `WormholeResult` shape), `sim.rs` (`try_wormhole_or_die` spawns the portal pair on a successful phase; new `sweep_portal_fx` retires them once the drain plus linger elapses), `state.rs` (`PortalFx`), `net.rs` (`portalFx` in the broadcast). Per-segment threading, the one-shot `teleport` flag, and the client's instant-snap prediction on that flag are all unchanged -- the client never predicted the landing itself, so no `predict.js` change was needed. Client: `public/js/render2d.js` (`drawPortals`), `public/js/render.js` (portal snapshot encoding), `wasm/renderer.ts` (portal region + ring/core emission, wasm rebuilt), `tools/bench/scene.js` (an entry/exit pair added to the parity scene). `powerups/README.md` was also rewritten to describe the live Rust implementation (types/hooks/config are now in `server-rust/src/powerups.rs` and `config.rs`) instead of the retired JS module-per-file structure, which the tree still keeps around as inert reference. Verified: `cargo build --release` clean, `tests/pw_wormhole.js` (9/9, including four new staged scenarios for the edge wrap, a dynamic-wall block with an enclosed escape-pocket bypass, the portal lifecycle through a full drain, and piercing an opponent's body), `tests/pw_headon.js`, wasm/2D pixel parity on every preset (worst case 0.013% differing pixels, well under the 1% bar), and the live browser smoke on both renderers.

#### Rust server rewrite, Node.js runtime dropped -- v4.0.0
- The entire game server was rewritten from JavaScript to Rust and now ships as a single compiled binary built from the new `server-rust/` crate. The module layout mirrors the old JS split one-to-one so the code stays navigable for anyone who knew the old tree: `src/main.rs` is the HTTP/WS entry point plus per-connection message handlers (the old `server.js`), and `src/config.rs`, `state.rs`, `sim.rs`, `lifecycle.rs`, `net.rs`, `highscores.rs`, `captcha.rs`, and `powerups.rs` carry the same functions (and largely the same comments) as their `server/*.js` and `powerups/*.js` counterparts. The wire protocol, the `/api/config` / `/api/captcha` / `/api/verify` endpoints, the config.json semantics (including shallow-merged section defaults), the highscores v1/v2/v3 store migrations, and every env hook (`SNAKE_CONFIG`, `SNAKE_PERF`, `SNAKE_TEST_SPAWNS`, `SNAKE_TEST_HOOKS`) are byte-compatible, so the stock client and the whole e2e suite run against the binary unchanged. Verified: all 19 `tests/pw_*.js` pass against the binary on the first attempt, and the live browser smoke (`tools/bench/run-smoke.js`, real captcha + join) passes on both renderers.
- Why "faster than node" panned out: on the same `tests/perf_baseline.js` matrix (four snakes, 1080p and 4k boards, body lengths 3/60/120), the movement step dropped from 24-177us average per call under the JS server to 4-14us under the binary, and the state broadcast from 138-240us to 27-47us -- roughly 5-12x across the board -- with worst-case spikes down as much as 60x (movement max 2494us -> 39us on the longest-snake 1080p scenario). Runtime-behavior notes, all deliberate: the death-respawn and captcha-expiry `setTimeout`s became deadline checks swept every sim tick (16ms granularity on 1.5s/120s timers, observably identical); unknown extra keys inside typed config sections are dropped rather than passed through (the opaque `clientFx`/`clientRender` blobs still pass through verbatim); and the grid object in the state broadcast no longer carries the resolved-away `preset` key.
- The listening port is now runtime configuration instead of a sed-patched source constant: the server reads config.json's new `"port"` key (default 8080), and a `PORT` environment variable overrides it -- a compiled binary cannot be text-patched the way `const PORT` in `server/config.js` was. `install.sh` writes the chosen port into config.json alongside `simHz`/`maxPlayers`/`enableDebug`, and its crash-loop port diagnostics read it back from there (legacy `const PORT` locations still checked for upgrades from older installs).
- `install.sh` no longer installs Node.js at all. It now installs the Rust toolchain via rustup, self-contained under `/opt/multisnake-toolchain` (nothing touches apt's package set beyond `build-essential`/`unzip`, and no developer `~/.cargo` is involved), plus Deno for the WASM renderer build, then compiles the server on the target host (`cargo build --release`, thin-LTO so the link stays inside a 1GB e2-micro) and installs the binary into `/opt/multisnake`. The update path sweeps the legacy JS runtime (`server.js`, `server/`, `powerups/`, `node_modules`) out of an existing install, and a new build-info.json is stamped from the source checkout's git metadata so a deployed server identifies its exact build instead of reporting "dev". `deploy/multisnake.service` execs the binary directly; `uninstall.sh` removes the toolchain directory. package.json survives as data only -- the server reads its `version` field for the build stamp.
- The dev/test tooling follows the binary: `tests/helpers.js` `startServer`, `tools/bench/run-smoke.js`, and `tools/bench/measure-corrections.js` all launch `server-rust/target/release/multisnake-server` when it exists and fall back to the legacy `deno ... --unstable-detect-cjs server.js` invocation when it does not (which keeps pre-rewrite git-worktree baselines runnable for the deferred Phase 14 measurement). The old JS server tree stays in the repo as reference for now. README and CONTRIBUTING run/deploy instructions were rewritten for the Rust toolchain, and the release workflow's stale "Node.js server" description was corrected (the release archive remains a source snapshot; install.sh builds the binary on the host).

#### Grid decay / anti-turtling obstacles -- v3.8.0
- Periodically the server telegraphs a warning at a chosen empty cell (`walls.telegraphMs`, default 3s -- a pulsing hazard-orange cue, not yet collidable), then it becomes a solid, indestructible 1x1 wall, lethal to any snake exactly like the board edge (same wall-grace stall / wormhole-rescue path as `resolveWallCollisions`, distinguished only by kill-feed cause `"obstacle"` vs `"wall"`). Unlike the original brainstorm pitch, walls are TEMPORARY: `walls.lifetimeMs` (default 45s) after going solid the wall despawns (with its own fade-out cue over the last `walls.despawnTelegraphMs`), so the board's topology keeps churning to break up a leader running an infinite safe loop instead of permanently shrinking the playable area over a long session.
- Presence- and interval-gated like the powerup pickup spawner: `walls.minPlayers` (default 2, matching blueShell/pinata's solo-play exemption), `walls.spawnIntervalMs` (15s) + `walls.maxConcurrent` (3) cap the cadence and live count. Cell choice is rejection-sampled: never on a snake/food/pickup/existing wall, never orthogonally touching another wall (an anti-sealing guard -- two walls can never chain into a line that could carve off an unreachable pocket of the board), never within `walls.minHeadDistance` (4) of a living snake's head (so a telegraph is never sprung directly under a nose even before its own countdown starts), and softly biased (`walls.leaderBias`, same shape as the rubberband food bias) toward the current leader's area so their loop gets disrupted most often.
- Server-authoritative: `server/state.js` (`S.walls`, `isSolidWallCell`, wall-aware `cellHasEntity`/`spawnAreaClear` so food/pickups/respawns never land on one), `server/sim.js` (`maybeSpawnWall`/`sweepWalls` in `simLoop`; `resolveWallCollisions`/`consumeInboundsTurn`/`applyDriftSlides` all now treat a solid wall cell exactly like out-of-bounds), `server/net.js` (broadcasts each wall's warn/solid/fading display state, derived fresh every tick from its stored telegraph/despawn timestamps), `server/config.js` + `config.json` (`walls` block). `server.js` gained a `spawnWall` test-hook op for deterministic e2e staging.
- Mirrored across both renderers for pixel parity: `public/js/render2d.js` (`drawWalls` -- pulsing hazard orange for the warning, opaque steel gray once solid, a faster pulse during the despawn fade) and `wasm/renderer.ts`/`public/js/render.js` (a new walls region appended to the snapshot memory layout; the header grew 8 bytes for the wall count, so every downstream snapshot offset in the facade now goes through named `SNAP_*` consts instead of ad-hoc arithmetic). `tools/bench/scene.js` exercises all three wall states; parity holds (~0.05% differing pixels). Test: `tests/pw_walls.js` (an instantly-telegraphed wall kills with cause `"obstacle"`; a long-telegraph wall stays passable while still in `"warn"`).

#### Speed-run / food-rate score mode -- v3.7.0
- A second, DEATH-INDEPENDENT scoring track alongside the existing length score: your best 5-minutes-of-food-per-minute rate over the session, its own leaderboard competed under both "Single PC" and "Networked" (`foodRateDaily`/`foodRateAllTime` per mode, highscores store bumped to v3 with a migration from v2). Unlike the length score, dying does NOT reset or lock this metric -- it keeps accumulating across every life on the same connection, by design: decoupling it from death encourages riskier, faster-paced play instead of turtling to protect a length score.
- Mechanics: each local seat gets an accumulator on its CONNECTION (`conn.foodRate[localIdx]`, created the first time that seat becomes a player) rather than on the game slot, because a slot is discarded and replaced on every spectate/rejoin cycle -- keying off the connection is what lets the metric survive both death/respawn and spectate/rejoin for the whole session. Play time is tracked in small buckets (`foodRate.bucketMs`, default 1000ms) that only close after that much ACTUAL PLAY time has elapsed -- a bucket simply never advances while the seat is spectating (a busy/full server queue, the respawn wait, etc.), which is what pauses the clock for free with no separate pause/resume bookkeeping. A rolling top-K of the best buckets ever seen (`foodRate.windowMs / bucketMs`, default 300 buckets = 5 minutes) is the "best 5 minutes, not necessarily one contiguous block" the mode is named for -- a worse new bucket is discarded, a better one evicts the current worst, so once the window fills the rate is monotonic non-decreasing.
- Provisional then locked: a live rate is shown from the very first tick, but it does not qualify for the leaderboard (and reads as `locked: false`) until `foodRate.floorMs` (default 300000 = 5 minutes) of actual play has accumulated; before that the number is a running average over whatever fraction of the window has closed so far and can drift either way as more of it samples in. Recorded at the same death/leave checkpoints the length score already uses (`recordIfQualifiesFoodRate` alongside `recordIfQualifies` in `server/lifecycle.js`), just without the length score's earned-length gate or its per-life reset.
- The underlying signal reuses the existing (previously dead-but-maintained) `s.score` increment sites in `server/sim.js` -- `applyMovementAndFood` (+1 per food) and `applyKillBonuses` (+`killBonusScore` per kill) -- via a new `bumpFoodRatePoints` hook, so no new per-food bookkeeping was needed. Server: `server/state.js` (the accumulator, bucket-closing, and snapshot/scoring helpers), `server/sim.js` (`advanceFoodRateTimers` once per sim tick, the two bump sites), `server/lifecycle.js` (`ensureFoodRateAcc` on join, `recordIfQualifiesFoodRate` on death/leave), `server/highscores.js` (v2->v3 migration, `qualifies`/`recordScore` generalized with a `kind` param), `server/net.js` (broadcasts the new boards plus a live `you.locals[].foodRate` snapshot for both playing and spectating locals), `server/config.js` + `config.json` (`foodRate` block: `enabled`/`bucketMs`/`floorMs`/`windowMs`). Client: `public/js/ui.js` (`updateLeaderboards` gained the new boards, `updateStatus` shows the live provisional/locked readout), `public/index.html` (the new board DOM under both leaderboard sections). Test: `tests/pw_foodrate.js` (provisional-before-floor + leaderboard recording, death-independence via the monotonic-once-locked property, and the spectator pause).

#### Kill feed / death attribution -- v3.6.8
- A Counter-Strike-style kill feed: whenever one snake causes another's death, a fading line appears ("EEA killed DEC") in a new bottom-left HUD stack (`#killFeed`), honoring the mobile UI-hide toggle. Server-authoritative: the death path in `server/sim.js` (`resolveWallCollisions`/`resolveSelfCollisions`/`resolveSnakeCollisions`/`tryWormholeOrDie`) now threads a `cause` (`wall`/`self`/`headon`/`body`) alongside the killer through the `died` map (`{ killer, cause }` per victim), and `handleDeath` (`server/lifecycle.js`) turns each into a one-shot kill event -- same broadcast-once-then-clear pattern as `S.explosions` (`server/net.js` `state.kills`). Initials come from the same session-bound `setInitials` values the leaderboards use, falling back to "???" for an unset seat.

#### Boost slide redesigned into a real drift (round fifteen) -- v2.1.1
- Redesigned the boost turn from a delayed input into a real drift, per the maintainer's spec. Old mechanic: a turn queued while boosting was tagged delay = slideDistance and the whole snake kept going straight for that many cells before the turn registered. New mechanic: the turn is applied to the HEAD immediately (verified e2e: dir flips on the very next movement step after the input), and instead the whole body keeps skidding one cell per movement step in the PREVIOUS travel direction for a time window -- so the head carves diagonally out of the corner while the body visibly slides sideways, a skid rather than an unresponsive input.
- Maintainer's three collision/tuning decisions, all implemented: (1) the drift window is TIME-based -- new config boost.driftMs (default 250) replaces boost.slideDistance, which is now ignored if an old config still carries it; (2) the skidding body is physical but CLAMPS at obstacles -- the per-step translation is skipped entirely (rigid body, no deformation) if it would push any segment out of bounds or into another snake, so the skid grinds against walls instead of killing its owner, while the drifted body stays fully solid to everyone else automatically since collision scans read live positions; (3) NO wall grace while boosting -- a boosted head aimed at a wall with no saving queued turn dies without the stall tick (verified e2e: death exactly 1 seq after reaching the last column boosted, exactly 2 seqs unboosted).
- Implementation: the body translation runs as a new applyDriftSlides pass at the top of movementStep (before new heads are computed, so the head extends from the translated front and the snake stays connected); the drift starts when a drift-flagged input (tagged at enqueue while boosting, same as before, so releasing boost right after the keypress doesn't cancel committed momentum) is applied in computeNewHeads, recording the pre-turn direction; the old inp.delay machinery is gone. The broadcast `sliding` flag now reflects the drift window, driving the existing slide-dust client effect unchanged. A wall-saving turn consumed early by consumeInboundsTurn deliberately does not start a drift.
- Client: predict.js still does not pre-play a turn typed while boosting -- previously because the landing tick was unknowable, now because the same server step also translates the body, which a one-cell follow-the-leader predictor cannot reproduce; behavior is identical, the reasoning comment changed. render.js segPixel's interpolation window widened from exactly-1 to 1-2 Manhattan so a drifting snake's diagonal segment steps still read as a glide instead of snapping. Debug panel shows driftMs where it showed slideDistance; the join-screen boost tip and README describe the new mechanic (including the no-mercy-at-walls rule).
- New e2e test tests/pw_boostdrift.js (Deno WS client against a live server, the standard harness): immediate head turn, sliding=true during the window with the head provably carried sideways while descending, drift expiry ending the sideways carry, boosted wall death with no grace, and the unboosted grace tick unchanged as a contrast case. - Added a powerups system: pickups spawn on the board on their own cadence (config powerups.spawnIntervalMs, capped at powerups.maxConcurrentPickups, default 1 at a time), each a distinct type with its own config block, all gated by an individual enabled flag. Every type's short player-facing description lives in its own module (powerups/*.js) and is served through /api/config, so the in-game help can never drift out of sync with what actually exists. The six types:
  - Wormhole: held in reserve as an independent charge -- no button. The instant a move would kill you (wall or another snake), it auto-fires, phasing you to the nearest safe spot or clear across the board, whichever is safer. One-time use; firing (even a failed landing) consumes it.
  - Growth Spurt: for a duration, food grows you twice as much and kills grant bonus length.
  - Speed Boost: a timed speed multiplier that stacks multiplicatively with the existing hold-to-boost.
  - Ice Trail: while active you lay a trail; anyone who crosses it (you included) slows more each time, floored so it never fully stops.
  - Poison Trail: while active you lay a trail; anyone who crosses it (you included) loses a segment, down to the global minimum length.
  - Blue Shell: activating it launches a seeking projectile at whoever is CURRENTLY longest -- even you, if you are the leader -- passing harmlessly through every other snake in flight. On impact the leader loses a large percentage of their length and it explodes, splashing a smaller percentage off nearby snakes. This makes leading risky and picking up every powerup no longer automatic. Shipped DISABLED by default (config powerups.blueShell.enabled: false) pending a more robust splash-damage test -- see README; the mechanic itself is complete and can be turned on by an operator.
- Inventory model: one held slot per player for the next non-wormhole powerup plus an independent wormhole charge. A pickup that would be wasted (slot already full of that type, or wormhole already charged) instead grants a food-like +1 segment. A per-seat activation key fires the held powerup (default Space for the arrows seat, Right Shift for the WASD seat); wormhole ignores the button entirely.
- Added a global minSnakeLength (default 3) that is now the single source of truth for BOTH the initial spawn length and the poison-trail damage floor, so the two can never drift apart.
- Trails and pickups are separate entity lists broadcast alongside food; trail tiles expire on the sim clock (not wall-clock timers), and a laid tile never permanently modifies a board cell. Food placement now also avoids spawning on top of an existing pickup.
- Client: pickups render as pulsing tiles, trails as dim tinted cells under the snakes, the blue shell as a moving projectile with an expanding explosion ring on impact, and a wormhole teleport snaps instantly (predict.js checks a one-shot teleport flag before its normal correction-glide path so a jump never animates as a slide across the board).
- Keybind remap UI (bottom-left corner panel, matching the existing debug/coop/leave button pattern): rebind each seat's activation key and swap which local index uses WASD vs. arrows. Persisted in localStorage, entirely client-side -- the server only ever learns which local index activated, never the physical key.
- Captcha/join screen: replaced the wormhole-only explainer with a single "What do the powerups do?" button whose popup is built from the server's powerupInfo and auto-sizes to however many powerups are enabled. Descriptions are short and ESL-friendly.
- Boost & slide follow-ups (same mechanic, shipped alongside): bumped the defaults to a more noticeable boostSpeed 2.0 / slideDistance 3; the debug panel now shows the live boost and slide amounts; added purely-cosmetic visual indicators (a jetstream behind a boosting head, a dust scatter during a slide drift), each gated by a clientFx flag; and fixed the "Got it" boost-tip button, which previously only dimmed the tip -- it now hides it outright and is fully independent of captcha state.
- Committed an end-to-end test suite (tests/pw_*.js): scripted Deno WebSocket clients that drive the live server and assert on real state broadcasts, one per powerup, using a shared retry harness for the inherently nondeterministic snake-steering setup. This round's test work found and fixed real bugs: the wormhole originally excluded a reversing escape direction (so it fizzled at walls), iceStacks was computed but never broadcast, and -- caught by the suite itself -- every pre-existing test needed to explicitly disable the newly-added blue shell so it wasn't collected by accident.

#### Generic hostname, TLS, and packaging (round two)
- Made the deployment hostname generic. The repository now ships a single Apache vhost template, deploy/fillmeout.example.com.conf, instead of a vhost named for one specific domain. The installer copies the template and substitutes the chosen hostname into /etc/apache2/sites-available/<hostname>.conf. The earlier fixed-name vhost was removed.
- Added an interactive hostname prompt to the installer. On the first run there is no default and a valid hostname must be entered. On a later run the previously used hostname, saved in /etc/multisnake/last-domain, is offered as the default and reused when the prompt is answered with an empty line. An explicit DOMAIN environment variable still overrides the prompt for non-interactive runs, and the prompt reads from the controlling terminal so it also works under the curl pipe.
- Added retirement of a previous hostname on the installer. When a repeat run uses a different hostname than the saved one, the installer disables and removes the old vhost files, including the certbot-generated -le-ssl variant, so an orphaned site is not left enabled alongside the new one.
- Added TLS provisioning to the installer using Let's Encrypt through certbot. The initial implementation used the HTTP-01 (port 80) challenge with the Apache plugin, then it was changed to the DNS-01 challenge through the Cloudflare API. DNS-01 was chosen because it needs no inbound port 80, so the DNS record can stay proxied through Cloudflare, whereas HTTP-01 fails when Cloudflare proxying or the Always Use HTTPS setting intercepts the challenge request. The Apache installer still writes the :443 vhost and the 80 to 443 redirect. The game is served on 443.
- Made TLS setup safe on hosts that already run certbot. Certbot and its plugins are installed only when certbot is not already present, so an existing certbot and its renewal schedule are left alone. The installer never edits certbot.timer or any cron job, since installing the Debian package already provides a twice-daily renewal timer that covers every certificate, including this one. If a certificate for the hostname already exists it is reused rather than reissued, which avoids rate limits and does not disturb other certificates.
- Added handling of the Cloudflare API token and email for TLS. The token can be provided as CF_API_TOKEN, reused from an existing per-hostname credentials file, or entered at a hidden prompt. It is written to /etc/letsencrypt/cloudflare-<hostname>.ini with mode 600 and reused at each renewal, since certbot records the path but not the contents. The email can be provided as CERTBOT_EMAIL or entered at a prompt, and a blank value registers without an email. TLS can be skipped entirely with ENABLE_TLS=no, and the propagation wait is adjustable with CF_PROPAGATION.
- Updated the uninstaller for the generic flow. It reads the hostname from /etc/multisnake/last-domain, or from DOMAIN if set, so it removes the correct vhost, certificate, and Cloudflare credentials file no matter which domain was used. It removes both the plain and the -le-ssl vhost files, deletes only this hostname certificate with certbot delete so other certificates and the shared renewal timer are untouched, removes the per-hostname credentials file, backs up the high score file to /root, and removes the installer state directory. REMOVE_CERT=no keeps the certificate and credentials.
- Added a source-snapshot release workflow. Because the project ships source only with nothing to compile, the workflow packages the tagged commit into .tar.gz and .zip archives with git archive and attaches both to a GitHub Release, rather than building binaries. Base token permissions are read-only with write elevated only on the release job, a concurrency group keyed on the tag prevents a re-pushed tag from racing an in-progress publish, and the publish step fails if no archive is produced. Action pinning to commit SHAs is left off by default with a directive to ask before enabling it, since pinned actions require ongoing maintenance the project does not have.
- Added community-health files filled in for this repository: a Code of Conduct based on Contributor Covenant 2.1, a Contributing guide with local test steps for the game, a Security policy pointing at GitHub Security Advisories, bug report and feature request issue templates with valid front matter, and a pull request template. Placeholder tokens for the project name and repository URL were replaced with the real values, and the security policy support table was converted to plain text to keep the files ASCII.
- Wrote the project README covering the feature set, requirements, the one-command install and uninstall, the interactive hostname prompt, the DNS-01 TLS flow with Cloudflare token scoping, the configuration keys, service operation, the repository layout, and the known limitations.

#### Port selection and failure detection (round three)
- Made the listening port dynamic instead of fixed at 8080. The installer selects a port before anything binds: an explicit PORT override if set, otherwise the port saved from the previous run, otherwise 8080, scanning upward until a free port is found. The chosen port is written into server.js and substituted into the Apache vhost alongside the hostname, and saved to /etc/multisnake/last-port for reuse. This was prompted by a real deployment where port 8080 was already held by another service on the host, which the earlier fixed-port installer could not accommodate. The vhost template and server.js still ship 8080 as their default placeholder, since that is the value the installer substitutes.
- Added a post-start health check to the installer. Because the systemd unit is Type=simple, systemd reports the service as started the moment it forks, so a crash immediately after (for example a port already in use) previously went unnoticed and the installer continued on to issue a certificate for a process that was not actually running. The result was a confusing 404 served by whatever else held the port. The installer now requests the app on its port after starting the service and aborts with the recent service logs if it does not answer.
- Added detection and recovery for a previously failed install. On a repeat run the installer checks whether the existing service is in a failed state or whether its logs show an address-in-use error. If so, it reports which port the failed install was using and which process currently holds it, explains that this is the likely cause of a 404 after the certificate step, and, when run interactively, asks for confirmation before selecting a free port and re-pointing the app and both Apache vhosts, including the certbot SSL vhost that certbot will not rewrite when the certificate is reused. This recovery path is separate from the proactive port selection, whose role is to prevent the clash on a clean run rather than repair an existing broken one.

#### Client netcode split and prediction (round four, Phase 2)
- Split the monolithic inline client into five ES modules under public/js: net.js (WebSocket transport and snapshot storage), predict.js (client prediction and reconciliation), render.js (canvas drawing), ui.js (captcha gate, status, high score lists, overlays, debug panel), and main.js (bootstrap and input). index.html loads them in dependency order. The installer already deploys the whole public tree, so the split deployed without a path change.
- Fixed a first-turn-only input bug. The client validated each new turn against a stale local heading, so after the first accepted turn later keypresses were rejected before being sent. The server now includes each player authoritative dir in the snapshot and the predictor adopts it, with a body-vector fallback for older snapshots.
- Removed all sub-cell interpolation. Rendering is grid-snapped to whole cells so motion is the classic discrete Snake step (tail cell drops, a cell appears at the head) rather than a smooth glide.
- Reworked the authority model to client-lead movement with server reconciliation. The client simulates its own snake from local input and renders that directly. The server stays authoritative for collisions, food, and score; it overrides the client position only on a real conflict (death or a respawn/teleport jump), never on ordinary one-tick timing differences.
- Added client-favoring wall grace on the server. A turn that avoids a wall is honored even if it arrives a tick late; the snake holds in place for a configurable number of grace ticks (wallGraceTicks) rather than dying to a late-by-a-hair input. Walls are static so this cannot be abused.
- Added input acknowledgment for true server reconciliation. Each client turn carries an incrementing sequence id (cseq); the server records the last sequence it processed per player and stamps it into each snapshot (you.ack). The client drops acknowledged inputs and replays only unacknowledged ones on top of the authoritative body. The server also acknowledges rejected turns (reversal, duplicate, buffer full) so the client stops retrying them, and resends unacknowledged turns after a couple of ticks to recover from dropped packets.
- Added client-side food prediction with rollback. The client predicts its own eat for instant feedback and hides that food, then confirms it when the server food changes and the body grows, or rolls the growth back if the server does not confirm within a few ticks. This addressed food that was not registering and food that appeared eaten while circling it.
- Fixed the repeated high-score prompt. Score is reset to zero on every respawn, and a zero or negative score never qualifies, so a respawned snake can no longer re-qualify with a stale score.
- Reworked the death and join lifecycle. On a qualifying death the player is gated on initials entry and cannot respawn until they submit; if they do not within initialsTimeoutMs (default 20 seconds) they become a spectator. Spectators sit in a global queue and are disconnected after spectatorIdleMs (default 5 minutes) of idle time. When a slot opens the front spectator is offered it with an explicit join button (joinOfferMs, default 10 seconds); if they do not accept, the offer passes to the next spectator, so an idle spectator cannot silently take a slot.
- Added an on-page DEBUG button and panel (no dev console needed). It shows client and server build stamps, the current sequence and tick, the pending input buffer, and recent server corrections. Recording is off until the panel is opened so there is no cost on the hot path. Every module registers a build stamp in a shared registry so a partial or stale deploy is immediately visible.
- Added Cache-Control headers on the Node static handler (no-cache for js, css, and html; no-store for the captcha API). A stale Cloudflare edge cache had been serving old JS after deploys; origin cache headers stop the edge from holding stale code.

#### Decoupled simulation rate (round five)
- Decoupled the server simulation rate from the snake movement cadence. A fixed loop runs at config simHz (default 60) and samples input every tick, while the snake advances one cell only when a movement accumulator crosses the current move interval. This lowers the input sampling delay to about one sim frame without changing snake speed, which is still governed by the movement cadence.
- Expressed the speed ramp as milliseconds per cell (config move.startIntervalMs, move.minIntervalMs, move.rampIntervalSec, move.rampStepMs) instead of the old tick-based speed block. Setting move.rampStepMs to zero gives a constant speed. Full state is broadcast only on movement ticks, so bandwidth is unchanged, and the network sequence still counts movement steps so client reconciliation is unaffected.
- Added a simHz prompt to the installer, defaulting to 60 and offering the last used value on repeat runs, saved to /etc/multisnake/last-simhz. It can be forced non-interactively with SIM_HZ, is validated as a positive integer in the range 1 to 1000, and is written into the deployed config.json with Node so the file stays valid JSON.

#### Prediction bounded to one cell and matched to server order, plus feel (round six)
- Fixed a rendering jitter regression in the client predictor. rebuild() had been advancing the locally rendered body by one cell every tick using the last known direction, even when there were no unacknowledged inputs queued, which left the rendered head a constant one cell ahead of the authoritative head and produced a visible wobble on ordinary straight-line movement and on turns. The predictor now renders the authoritative body exactly whenever its local input queue is empty, so no input means no prediction and the server can never appear to lag behind or override a plain straight run.
- Bounded client prediction to exactly one cell ahead of the authoritative body at all times. An intermediate fix had instead replayed one cell per queued input, which produced a visible multi-cell jump whenever a second turn was queued before the first was acknowledged. Also stopped the debug panel from logging a false correction on ordinary straight-line movement with an empty input queue: comparing a deliberately un-advanced prediction against a snapshot that had naturally moved forward on its own is not a misprediction, and was being misreported as one.
- Switched the one-cell prediction from the most recently queued turn to the oldest unacknowledged one. The server always applies queued turns in the order it received them, so predicting off the newest turn guessed a direction the server had not reached yet whenever two turns queued up before the first was acknowledged. This produced a diagonal, perpendicular-direction resync on the very next snapshot even though nothing was actually wrong, and was especially visible during ordinary rapid turning.
- Mirrored the server's wall-grace turn selection in the client predictor. When the oldest queued turn would carry the head out of bounds, the server already searches the remaining queued turns for the first one that stays on the board; the client had no equivalent logic and would predict the out-of-bounds turn the server was never going to use, producing the same kind of spurious diagonal resync, clustered specifically near the map edges. The client now performs the identical search.
- Fixed an unacknowledged input getting stuck at the front of the local input queue forever once it had exhausted its retries with no server acknowledgment, most likely from an occasional dropped WebSocket frame. Left in place, a single permanently stuck turn poisoned every future one-cell prediction and the food-eat prediction check, since both always read the oldest queued entry; this was the cause of a persistent stream of resyncs unrelated to walls or turning frequency, and of food not appearing to register an instant eat despite the server crediting it correctly. The client now drops an input once its retries are exhausted and falls back to trusting the authoritative body.
- Made the client's misprediction detection run regardless of whether the debug panel is open, rather than only while recording. The debug panel's own logging is unchanged and still only records while open; the detection itself now always runs because the correction glide effect below needs it available all the time.
- Disabled Nagle's algorithm on the server's WebSocket connections by setting TCP_NODELAY on the raw socket during the upgrade handshake. The server's frequent, small game-state broadcasts and direction messages could otherwise sit buffered by the kernel for tens of milliseconds waiting to be coalesced with more outbound data before being sent, adding avoidable round-trip latency for no benefit on a connection that is already small and frequent by nature. This does not address propagation delay or Cloudflare edge latency, only kernel-level buffering on the origin server itself.
- Added a clientFx block to config.json (inputFlash, inputFlashMs, correctionGlide, correctionGlideMs) served read-only to the client through a new GET /api/config endpoint, with hardcoded defaults on the server so the feature stays on even against an older config.json that predates the key. This is the only configuration surface for the two effects below: a single global on/off per effect for the operator, with no per-player setting and no client-side prompt.
- Added an input flash effect. The instant a keypress is accepted, a short fading strip is drawn on the leading edge of the player's own head cell in the pressed direction. It is timed purely by elapsed time since the keypress rather than by network ticks or by whether the body actually steps that tick, which is what makes it register as instant regardless of round-trip time.
- Added a correction glide effect. When a one-cell misprediction is corrected, the player's own head eases from the mispredicted cell to the corrected cell over a short configurable duration instead of snapping. This is a narrow, deliberate exception to the project's grid-snapped rendering; it applies only to the local player's own head cell during the correction window, and every other segment, every other player, and every other frame remain exactly grid-snapped as before.
- Considered and rejected moving to a hybrid authority model where the client reports its own position for moves the server can classify as uncontested (no food, no collision), with the server validating only contested moves. Rejected because it does not reduce latency, since the server still cannot approve a packet it has not received yet, contested or not, and it trades away the server's current full authority over position, which is what currently makes every leaderboard score impossible to fake, for a cheating surface that would need closing again per powerup once movement stops being simple axis-aligned steps. Server remains authoritative for all positions.

#### Couch co-op fairness correction: strict round robin (round eight)
- Corrected a design mistake from round seven: a co-op connection's second local seat previously always respawned immediately on death, bypassing the spectator queue entirely regardless of who else was waiting. That let one connection occupy two board slots indefinitely while other people sat queued, which is exactly the kind of hogging the operator does not want -- every local seat needs to be round-robin fair on its own, with no advantage for co-op.
- Replaced the connection model again: connections no longer have a single role/slots pair, or even a single conn.slots array. Each connection now has a locals array indexed by local index, and each entry independently holds either { role: "player", slotIndex } or { role: "spectator", slotIndex: null }. A connection's two seats can be in different roles at the same time -- p1 playing while p2 sits in the spectator queue is normal, not an edge case.
- The spectator queue and join-offer mechanism now operate on (connId, localIndex) pairs instead of connId alone, so each local seat waits its own turn independently. admitLocal() is the single admission path for both a fresh connect and a joinLocal request: take a free slot immediately only if no one else is waiting, otherwise join the back of the same queue everyone else uses. joinLocal essentially never fails outright anymore (aside from the maxLocalPlayers cap) -- it either seats the new local player immediately or queues it fairly, exactly like a fresh connection would be treated.
- respawnOrSpectate() lost its co-op special case entirely: a slot yields to the spectator queue on death under the exact same rule regardless of whether it's a solo connection's only seat or one seat of a co-op pair. The connection's other seat, if any, is never affected by what happens to this one.
- The state broadcast's per-connection payload changed again: you.role/you.slots (round seven) is replaced by you.locals, an array of per-seat { role, slot, ack } or { role, queuePos, queueLen } entries. There is no longer a single top-level role for a connection, since the two seats can now genuinely differ.
- Client-side, this meant tracking curr.you.locals per local index in main.js instead of a single myRole.role, and reworking ui.js's initials/spectator/join-offer overlays to take an isCoOp flag: a genuine solo connection keeps the original full-screen prompt, but once co-op is active, either seat could need a prompt while the other keeps playing, so both switch to small non-blocking corner panels instead.
- One known simplification, not yet live-tested: if a queued co-op seat's idle-spectator timer expires while the connection's OTHER seat is still actively playing, that seat just quietly drops out of the queue rather than the whole connection being disconnected (which would incorrectly eject the still-playing seat too). Flagged in TODO.md.
- Re-verified the connection/seat bookkeeping against a new scratch headless harness (round seven's harness is now stale and was replaced, not extended, since the underlying model changed): solo + co-op admission, a co-op seat correctly queuing behind an already-waiting spectator instead of jumping ahead, strict first-in-line-wins ordering when a slot frees up, and a co-op seat's death yielding to the queue exactly like a solo seat's would. Not committed, per the existing tests/ note in TODO.md.

#### Leave flow, high-score state machine, boost/slide, idle cleanup, latency pass (round ten)
- Added an explicit "Leave" flow. A new leaveLocal message removes ONE local seat completely: its board slot is freed (or its spectator-queue entry dropped), and the seat becomes a null hole -- it is deliberately NOT pushed into the spectator queue. Rejoining requires a fresh joinLocal, which now fills the leaver's old hole first so the key maps (0 = arrows, 1 = WASD) stay stable. Leaving the LAST seat on a connection tears the whole connection down and closes the socket: the client shows a menu/rejoin screen (Play reloads and re-runs the captcha gate) instead of idling on a dead board. The client renders one Leave button per existing seat, kept in sync every state broadcast.
- Replaced the per-slot initials prompt state (awaitInitials/initialsDeadline) with a connection-scoped high-score state machine: conn.pendingInitials (queue of { local, targets, score }) plus conn.activeInitials (the one prompt on screen, with its deadline). A qualifying score is BANKED on death, and also on leave if the seat left mid-game with a qualifying score. Prompts are never shown while any local seat on the same connection still has a living snake (shared-keyboard rule); once nothing is alive, they flush one at a time, each with a fresh countdown. A seat that dies while a flush is owed is parked as role "held" -- its slot is freed for round-robin fairness -- and every held seat is re-admitted through the normal admitLocal path once the queue drains, so P1 resumes solo play after entering initials. Leaving during your own live prompt counts as declining it and advances the flush.
- Hardened the initials handler while rewriting it: the server now records the score and boards it tracked for the active prompt and ignores the client-supplied score/targets fields, so a client can no longer submit a fabricated score to the leaderboards.
- Expanded the inactivity timeout to active multiplayer play: each slot tracks lastInputAt (updated by dir and boost messages), and when EVERY living snake has been silent for config playerIdleMs (default 120000), the sweep disconnects the idle connections like the spectator idle rule does. lastInputAt is deliberately not reset on automatic respawn, so an AFK player who keeps dying and respawning cannot keep resetting their own clock; one attentive player keeps the lobby alive for everyone.
- Made the build number real instead of a hand-edited string constant. server.js resolves its build at startup: commit count + short hash from git in a live checkout, else a build-info.json stamped by git archive export-subst (new .gitattributes entry) in release archives, else package.json version marked "dev". The result is broadcast in every state message and shown in the existing debug panel's server build line, so a stale deploy is immediately visible.
- Added a boost-with-inertia mechanic (config boost.enabled/boostSpeed/slideDistance, defaults on/1.5/2). Holding the key of the current travel direction boosts that snake: movement accumulators are now PER SNAKE, and a boosting snake's accumulator fills boostSpeed times faster against the shared ramped interval. The trade-off is the slide: a turn queued while boosting is tagged with delay = slideDistance and drifts that many further straight cells before registering (the wall-grace lookahead may still consume it early to avoid a wall death, intentionally). Collision stayed step-synchronous: movers are checked against EVERY living snake, with a non-mover's body (tail included, since it does not vacate) as a solid obstacle and head-on death only between two snakes moving the same step. Client-side, a held-key detector sends only boost on/off transitions, and turns typed while boosting are sent and acked normally but flagged so the predictor does not pre-play a turn whose landing tick only the server knows.
- Added operator-configurable zero-overhead debug (config enableDebug, default true). Server: a single dlog binding that is null when disabled, so every call site is one falsy short-circuit -- no strings built, nothing buffered. Client: /api/config now carries enableDebug, and when false the DEBUG button, panel, refresh timer, and correction recording are simply never constructed.
- Added client-side lock-step render smoothing (config clientRender.interpolate, default true, served via /api/config). The state broadcast now includes each player's effective ms-per-cell (moveMs, boost included), and render.js eases every server-rendered snake segment from its previous-snapshot cell to its current cell over exactly that interval, so travel is smooth and in step with the server cadence instead of jumping a whole cell per broadcast. Local predicted bodies keep the existing prediction/glide path; teleport-sized jumps (respawn, growth) snap. This reverses round four's "no sub-cell interpolation" decision at the operator's request, as a purely cosmetic client setting -- server collision and authority are untouched.
- Latency/perf pass over the hot paths: state broadcast now serializes the shared board once and splices each connection's small you payload into the JSON string (was a full re-stringify per connection); spectator queue positions are precomputed per broadcast instead of a findIndex per seat per connection; collision scans use index loops instead of slice().some() allocations; the sim loop schedules against an absolute next-tick time so timer jitter no longer accumulates into a slower effective tick rate; permessage-deflate is now explicitly disabled on the WebSocket server with the reasoning documented.
